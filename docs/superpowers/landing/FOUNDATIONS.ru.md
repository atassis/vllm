# Основы — из чего состоит LLM и зачем нужна каждая часть

> **Для кого этот документ.** Для сильного software engineer'а, который *не знаком с ML-внутренностями*.
> Вы знаете, что такое токен, видели цепи Маркова и конечные автоматы, умеете читать
> матричную математику — но до сих пор потребляли AI, а не строили. Этот документ даёт
> ментальную модель, которую предполагают все остальные доки. После него `PIPELINE-NARRATIVE.md`
> (системная история) и `PIPELINE.md` (точная карта) встанут на место, потому что вы уже
> будете знать, *что* такое embedding / layer / head / KV cache, **прежде чем** читать,
> *как* vLLM их планирует и разбивает на страницы.
>
> **Лестница.** `FOUNDATIONS.md` (этот — что представляет собой модель) → `PIPELINE-NARRATIVE.md`
> (почему система обслуживания устроена именно так) → `PIPELINE.md` (где всё живёт,
> `file:line`) → `SPEC-PP-INVARIANTS.md` (что нельзя ломать при изменениях).
>
> **Как читать.** Нарратив, сверху вниз, с примерами. Математика подана интуитивно, но
> честно — там, где формула оправдывает своё место, она есть, с пояснением каждого термина.
> Якоря на код (`file:line`) приведены, чтобы вы сразу видели мостик от концепции к дереву
> vLLM, но открывать их при первом чтении не обязательно.

## 0. Начнём с того, что вы уже знаете: цепь Маркова

Вы знаете цепь Маркова: вы в каком-то состоянии, и фиксированная таблица вероятностей
говорит, каким будет следующее состояние. «Погода завтра зависит только от погоды сегодня.»

LLM — та же форма, но с тремя улучшениями:

1. **«Состояние» — это весь текст до текущего момента**, в виде последовательности токенов, а не
   только последний символ. (Так что это очень высокопорядковая цепь Маркова.)
2. **Вероятности переходов не хранятся в таблице — они *вычисляются*** большой обученной
   функцией (нейронной сетью). Таблица для «всех возможных текстов» была бы бесконечной;
   сеть сжимает её в ~миллиарды чисел (веса).
3. **Результат — распределение вероятностей по следующему *токену***, из которого вы выбираете
   один, добавляете его и повторяете.

Этот цикл — вся игра:

```
tokens so far  ─▶  model  ─▶  probability over the next token  ─▶  pick one  ─▶  append
       ▲                                                                          │
       └──────────────────────────────────────────────────────────────────────────┘
```

Это называется **авторегрессией** ("регрессия по собственному прошлому выводу"). Всё
остальное в этом документе — embeddings (эмбеддинги), attention (внимание), KV cache,
head — это просто *то, что находится внутри блока «model»*, а всё в доках vLLM — о том,
как выполнять этот цикл для **тысяч последовательностей одновременно, быстро, при
ограниченной GPU-памяти, не портя вывод.**

Запомните одно число: типичная модель за один проход производит **один токен**.
Этот единственный факт обусловливает почти каждое дизайнерское решение дальше (именно
поэтому decode медленный, именно поэтому KV кэш существует, именно поэтому speculative
decoding того стоит).

## 1. Токены → эмбеддинги: превращаем символы в геометрию

**Токенизация.** Текст сначала разбивается на **токены** — подсловные куски, каждый с
целочисленным id. `"unhappiness"` может стать `["un", "happ", "iness"]` → `[1023, 5519,
8841]`. Словарь фиксирован (например, 250 000 токенов для Qwen3.5). Думайте о token id как
о «номере строки».

**Почему нельзя подавать id напрямую.** Id `5519` — просто индекс, в нём нет смысла.
`5519` не «больше» и не «ближе к» `5520` в каком-либо полезном смысле. Сети нужен *смысл,
выраженный через геометрию*: похожие токены должны быть близкими точками в пространстве,
чтобы математика (скалярные произведения, суммы) могла оперировать смыслом.

**Эмбеддинг — это таблица поиска.** Это матрица размера `[vocab_size, hidden_size]` —
по одной строке на токен, каждая строка — вектор из `hidden_size` чисел с плавающей
точкой (например, 5120). «Заэмбеддить токен 5519» буквально означает «взять строку 5519».
Эти строки *обучены* во время тренировки так, чтобы, например, векторы для «king» и
«queen» оказались связаны.

```
token id 5519  ──lookup──▶  [0.21, -1.03, 0.44, … , 0.07]   (a 5120-dim vector)
                            └──────── this token's "meaning vector" ────────┘
```

**Почему это важно для vLLM (мостик).** Эта таблица огромна: `250k × 5120 × 2 байта
≈ 2.4 ГБ` только для эмбеддинга. В vLLM это `VocabParallelEmbedding`
(`vllm/model_executor/layers/vocab_parallel_embedding.py:192`). Когда вы читаете в
заметках проекта, что «A1c квантует эмбеддинг *черновой* модели до int4», теперь вы
точно знаете, что именно сжимается и почему это даёт ~1.8 ГБ — это именно эта таблица,
продублированная для speculative draft-модели. (И квантование *безопасно* — почему, мы
увидим в §7.)

На выходе этого этапа последовательность превращается в стек векторов:
`[num_tokens, hidden_size]`. Этот блок чисел называется **hidden states** (скрытые
состояния) — рабочее представление текста в модели. Оно будет трансформироваться слой
за слоем.

## 2. Слои (transformer blocks): где происходит «мышление»

Модель — это **стек одинаковых блоков** (например, 64 штуки). Каждый блок принимает
hidden states и выдаёт уточнённые hidden states той же формы. Укладка в стек позволяет
модели строить всё более абстрактные представления — ранние слои ≈ синтаксис, поздние
слои ≈ смысл/задача (грубо).

Каждый блок делает **два** дела:

### 2a. Attention (внимание) — смешиваем информацию *между* токенами

Это сердце transformer'а, и единственная концепция, на которой стоит притормозить.

До сих пор вектор каждого токена знал только *о себе самом*. Но «it» в «the cat sat
because **it** was tired» нужно оглянуться назад и найти «cat». **Attention** — это
механизм, с помощью которого токен может *посмотреть на предыдущие токены и взять
взвешенную смесь их информации.*

Для каждого токена блок вычисляет три вектора из его hidden state через обученные матрицы:
- **Query (Q)** — «что я ищу?»
- **Key (K)** — «что я предлагаю, как то, на что могут смотреть?»
- **Value (V)** — «фактическая информация, которую я отдам, если на меня обратят внимание».

Затем, для токена *i*:
1. Сравниваем его **Q** с **K** каждого предыдущего токена (скалярное произведение) →
   оценка релевантности для каждого прошлого токена. Высокая оценка = «этот токен мне
   релевантен».
2. Softmax этих оценок → веса, сумма которых равна 1.
3. Выход = взвешенная сумма векторов **V** прошлых токенов.

В одну строку (знаменитая формула), для всей последовательности сразу:

```
Attention(Q, K, V) = softmax( Q·Kᵀ / √d ) · V
```

- `Q·Kᵀ` — запрос каждого токена, умноженный скалярно на ключ каждого токена → сетка
  `[n × n]` оценок релевантности.
- `/ √d` — масштабирование, чтобы softmax не насыщался (d = размерность head'а).
  Техническая деталь.
- `softmax(...)` — превращает каждую строку оценок в веса с суммой 1.
- `· V` — смешивает значения с этими весами.

**Каузальная маскировка.** Токен может смотреть только *назад* (нельзя смотреть на слова,
которые ещё не сгенерированы). Поэтому верхний треугольник сетки `[n × n]` маскируется
в ноль. Именно поэтому это называется «causal self-attention».

**Heads (головы).** Всё это выполняется параллельно несколькими **attention heads**,
каждый со своими матрицами Q/K/V, так что разные головы могут специализироваться («одна
отслеживает подлежащее, другая — позиции»). Их выходы конкатенируются. Это и есть
«multi-head» в «multi-head attention».

### 2b. MLP / feed-forward — трансформируем *каждый* токен

После того как attention перемешал информацию между токенами, маленькая двухслойная
нейронная сеть (**MLP** или **feed-forward** блок) применяется к *вектору каждого токена
независимо* — «теперь, когда ты собрал контекст, улучши себя». Здесь живёт большая доля
параметров.

### 2c. Сантехника, делающая глубокие стеки обучаемыми

- **Residual connections**: каждый блок добавляет свой выход к своему входу (`x + block(x)`)
  вместо того, чтобы заменять — так информация и градиенты проходят через 64 слоя, не
  исчезая. (Именно этот `residual` вы увидите, путешествующим между PP-стадиями.)
- **Нормализация** (RMSNorm/LayerNorm): перемасштабирует векторы, чтобы числа оставались
  стабильными.

**Мостик.** В vLLM пара `{hidden_states, residual}` на каждый токен — это именно то, что
пересекает границу pipeline-parallel стадии (`vllm/sequence.py:12`, `IntermediateTensors`)
— теперь вы знаете, что это просто «рабочее представление, в середине стека, переданное
GPU, который хранит следующие слои».

## 3. KV cache — самая важная системная идея, и *почему*

Это концепция, которая объясняет 80% машинерии памяти vLLM. Поймите её — и остальные
доки откроются.

**Проблема.** Чтобы сгенерировать токен N+1, attention (§2a) нужны **K** и **V** каждого
предыдущего токена, на *каждом* слое. Если пересчитывать K и V для всего префикса на
каждом шаге, генерация ответа из 1000 токенов обошлась бы в ~1000× больше работы attention
— O(n²) суммарно. Мучительно медленно.

**Инсайт.** K и V прошлого токена **никогда не меняются** после вычисления. Ключ токена
5 — это ключ токена 5 навсегда. Поэтому **вычислите их один раз и закешируйте.** На каждом
новом шаге новый токен вычисляет только *свои* Q, K, V, добавляет K/V в кэш и обращает свой
Q к *всему закешированному* K/V.

```
step N:   new token computes Q,K,V  →  append K,V to cache  →  attend Q over ALL cached K,V
                                          (cache grows by 1 token × every layer)
```

Таким образом decode становится **O(1) пересчёта за шаг** — но ценой: нужно **хранить**
K и V для каждого токена × каждого слоя × каждого attention head'а. Это хранилище —
**KV cache**, и для длинных последовательностей он **доминирует в GPU-памяти** —
больше, чем веса модели.

**Теперь каждое решение vLLM о памяти очевидно:**
- KV cache огромен и привязан к запросу → нельзя давать каждому запросу буфер
  фиксированного максимального размера (расточительство + фрагментация) → **PagedAttention**
  хранит его в фиксированных **блоках** с **block table** на каждый запрос, как виртуальная
  память ОС. (`PIPELINE.md` §7.)
- Блоки могут закончиться посреди шага → планировщик должен **вытеснять** (preempt) запросы.
- Идентичные префиксы (одинаковый system prompt) могут **разделять** блоки → **prefix caching**.
- Speculative draft имеет свои *собственные* K/V (собственный attention layer), но разделяет
  block tables — это и есть тема brick 30.

**Число, чтобы прочувствовать масштаб:** для 7B-модели при нескольких тысячах токенов
контекста KV cache часто занимает несколько ГБ *на* каждый конкурентный запрос. На GPU
с 16 ГБ «сколько KV-блоков влезет» *и есть* «сколько запросов я могу обслуживать
одновременно». Вот почему worker выполняет профилирующий проход для определения размера
`num_gpu_blocks` (`PIPELINE.md` §7) раньше всего остального.

## 4. Head и logits — превращаем вектор обратно в токен

После последнего блока каждая позиция имеет финальный вектор hidden state — полностью
готовое представление модели о том, «что идёт следующим». Чтобы превратить это в настоящий
токен, нужен ещё один шаг.

**LM head** — это матрица размера `[hidden_size, vocab_size]`. Умножение финального вектора
hidden state на неё даёт одну оценку для каждого токена словаря — **logits** (логиты):

```
final hidden vector  ──LM head ([hidden × vocab])──▶  logits = [score per token, ×250k]
```

- **Logits** — сырые, неограниченные оценки. `softmax(logits)` превращает их в
  распределение вероятностей по словарю.
- **Сэмплирование** выбирает фактический следующий токен:
  - **Greedy / argmax** — берём токен с наибольшим logit. Детерминировано.
  - **Temperature / top-p / top-k** — сглаживают или ограничивают распределение и
    сэмплируют случайно, ради разнообразия.

**Два мостика, которые пригодятся позже:**
1. LM head часто **привязан** к таблице эмбеддингов (те же веса, транспонированные) —
   одна матрица делает «id → вектор» на входе и «вектор → оценки» на выходе. (Именно
   поэтому в заметках проекта говорится, что draft «разделяет lm_head таргет-модели».)
2. Детерминированность `argmax` — *это* крючок, на котором держится корректность
   speculative decoding (§7): жадный вывод — фиксированная функция от logits, поэтому
   токен черновика «правильный» тогда и только тогда, когда он равен argmax таргета.

В vLLM это `compute_logits` + сэмплер; head живёт только на **последней** pipeline-стадии
(эмбеддинг — только на **первой**) — что, теперь, когда вы знаете, что каждый из них
делает, является естественным местом для них.

## 5. Один полный проход, от начала до конца

Собрав §1–§4 вместе, вот один forward pass, производящий один токен:

```
token ids
   │  §1 embedding lookup            [n, hidden]
   ▼
 ┌─────────────────────────────────────────────┐
 │  block 1:  attention (over KV cache) + MLP   │  §2
 │  block 2:  …                                 │
 │   …  (×64)                                    │
 └─────────────────────────────────────────────┘
   │  final norm                     [n, hidden]
   ▼
   §4 LM head → logits [n, vocab]  →  take the LAST position's logits
   ▼
   sample (argmax / temperature)  →  next token id
   ▼
   append to the sequence, write this step's K/V into the cache, and loop  (§0, §3)
```

Это полная языковая модель. **Prefill** (предзаполнение) = прогнать всё это через весь
промпт сразу (заполняет KV cache для всех токенов промпта, производит первый новый токен).
**Decode** (декодирование) = прогонять по одному токену за раз (каждый шаг добавляет один
K/V в кэш). Планировщик vLLM намеренно *стирает* различие prefill/decode — он просто
отслеживает «сколько токенов этого запроса уже вычислено» — это идея «без фаз» из
`PIPELINE-NARRATIVE.md` §Move 1/3.

**Почему decode медленный (и почему нам не всё равно).** В decode вы прокачиваете *все*
веса и *весь* KV cache через GPU, чтобы произвести *один* токен. Вычислительные блоки GPU
в основном простаивают, ожидая данных из памяти — decode **ограничен пропускной
способностью памяти** (memory-bandwidth-bound), а не вычислениями. Этот единственный факт
является всей мотивацией для следующих двух разделов.

## 6. Pipeline parallelism в одном абзаце (вы это уже понимаете)

Модель (§2) — стек слоёв. Если она не помещается на одну GPU, **разделите стек**:
GPU0 хранит слои 0–k (и эмбеддинг, §1), GPU1 хранит слои k–end (и head, §4). Hidden state
токена течёт GPU0 → GPU1 один раз на каждой границе (`IntermediateTensors` из §2c). Это
**pipeline parallelism (PP)**. Альтернатива — tensor parallelism — делит *каждый* слой
и должна синхронизироваться на *каждом* слое: нормально поверх быстрого NVLink, смертельно
поверх медленного PCIe. Полная история: `PIPELINE-NARRATIVE.md` §Move 4. Единственное, что
нужно вынести отсюда: при PP эмбеддинг находится на первой GPU, head — на последней, а
speculative draft (следующий раздел) естественно живёт на последней GPU, потому что именно
там уже находится финальный hidden state.

## 7. Speculative decoding и MTP — наконец, проект в контексте

Теперь та часть, о которой весь проект.

**Возможность.** Decode ограничен памятью (§5): производство одного токена едва использует
вычислительную мощь GPU. Итак — *можем ли мы проверить несколько кандидатных токенов почти
за ту же цену, что и один?* Если у нас уже есть угадка для нескольких следующих токенов,
таргет-модель может верифицировать их все за **один** forward pass (attention по тому же KV
cache, просто чуть больше позиций — почти бесплатно на GPU, ограниченном памятью).

**Загвоздка.** Нельзя знать токен N+1 до того, как произведён токен N — это авторегрессия
(§0). Поэтому нужен **дешёвый угадчик** («черновик», draft) и способ **верифицировать**
его угадки, не меняя результат.

**Черновик (drafter).** Существует несколько видов (n-gram, EAGLE, draft-model), но наш —
это **MTP = Multi-Token Prediction**. Обычная модель предсказывает *один* следующий токен
из финального hidden state (§4). MTP прикручивает маленький дополнительный модуль — свой
маленький эмбеддинг + один дополнительный transformer layer + *разделяемый* head, — который,
получив **тот же финальный hidden state, что только что произвела таргет-модель**, предсказывает
токен *после* следующего. Потому что:
- его входные данные (hidden state таргета) уже вычислены → **бесплатно**,
- он крошечный (один слой) → **дёшево**,
- он обучен имитировать таргет → его угадки часто правильны (~71% принято на llama.cpp),

он — отличный генератор черновиков. В vLLM это модель вроде
`vllm/model_executor/models/qwen3_5_mtp.py`. Теперь вы можете читать brick 20 («у черновика
есть свой эмбеддинг») и brick 30 («черновик переиспользует hidden state таргета, живущий на
последнем ранге») — и они будут значить что-то конкретное.

**Верификация (почему это доказуемо корректно).** **Rejection sampler** — это оракул.
В жадном режиме правило таково:

> токен черновика **принимается** тогда и только тогда, когда он равен `argmax` таргет-модели
> на этой позиции; иначе он **заменяется** на argmax таргета, а все последующие черновики
> выбрасываются.

Пройдитесь по тому, почему это идентично обычному жадному декодированию: обычное жадное
*выдало бы* argmax таргета на каждой позиции. Если черновик угадал правильно — отлично,
мы пропустили его пересчёт. Если черновик угадал неверно — подставляем правильный argmax,
поэтому выданный токен *всё равно* в точности тот, что выдало бы жадное. Черновик только
сохраняет работу; он никогда не может изменить ответ. (`vllm/v1/sample/rejection_sampler.py:708`
и `:452`.)

**Два следствия, которые движут проектом:**
1. **Агностицизм к весам.** Поскольку корректность зависит только от (argmax таргета,
   угадка черновика), *качество* черновика меняет только частоту принятия — никогда не
   меняет вывод. Это лицензия делать черновик **lossy** (с потерями): квантование 2.4 ГБ
   эмбеддинга черновика до int4 (A1c) может только снизить acceptance, никогда не
   испортит текст. Именно поэтому dummy/MiMo-веса валидны для *тестирования* механики.
2. **Бонусный токен и сетка.** Если *все* K черновиков приняты, таргет даёт ещё один
   «бесплатный» токен (он всё равно вычислил те logits). Поэтому вывод сэмплера — это
   сетка `[num_reqs, num_spec+1]`, валидные токены упакованы слева, заполнение `-1`
   справа. Этот `-1` и переменная ширина — именно то, что должно корректно пережить
   пайплайн — это баги, которые фиксирует проект (`PIPELINE-NARRATIVE.md` §Move 7).

**Почему «spec × PP × async» сложно (формулировка в одном предложении, которое вы теперь
можете разобрать):** черновик производится на *последней* GPU, но *более ранним* GPU
нужны результирующие токены, чтобы построить вход следующего шага; а поскольку движок
пайплайнит `pp_size` шагов вперёд, бухгалтерия черновиков на каждом шаге (те самые
placeholder'ы `-1`) должна оставаться корректной через задержку в несколько шагов.

## 8. Компактный математический букварь

Ровно столько, чтобы следить за статьями и рассуждать вслух — линейная алгебра у вас уже есть.

- **Всё — matmul.** Hidden states — это матрица `[n_tokens, hidden]`. Линейный слой — `X·W`.
  Attention и MLP — стеки таких операций. «В модели N миллиардов параметров» = суммарный
  размер всех матриц `W`.
- **logits → вероятности.** `softmax(z)_i = e^{z_i} / Σ_j e^{z_j}` — потенцируем и
  нормируем, чтобы оценки стали распределением. `argmax` берёт наибольший; **температура
  T** делит logits на T перед softmax (T<1 заостряет → более детерминированно, T>1
  сглаживает → более случайно); **top-p** оставляет только наименьший набор токенов,
  чьи вероятности дают в сумме p.
- **attention** `softmax(QKᵀ/√d)·V` — §2a, термин за термином. `QKᵀ` — это `[n, n]`
  (каждый токен против каждого), вот почему длинные контексты дорогие и почему KV cache
  (кеширующий K, V) — ключевая оптимизация.
- **compute-bound vs memory-bound.** Prefill обрабатывает много токенов сразу → много
  matmul на каждый загруженный байт → **compute-bound**. Decode обрабатывает один токен,
  но должен перезагрузить все веса + KV → мало matmul на байт → **memory-bound**.
  Speculative decoding эксплуатирует именно это: дополнительные кандидатные токены почти
  бесплатны на шаге, ограниченном памятью.
- **почему rejection sampling точен** (случай без жадности, для полноты картины): чтобы
  сэмплировать из целевого распределения `p`, предлагая из черновика `q`, принимаем токен
  черновика `x` с вероятностью `min(1, p(x)/q(x))`, а при отклонении сэмплируем из
  нормированной положительной части `p−q`. Математика гарантирует, что финальные сэмплы
  распределены в точности как при выборке из `p`. Жадный (§7) — вырожденный случай, когда
  `p` — пик на argmax, что сводится к «принять тогда и только тогда, когда равны.»
  (Статьи: Leviathan et al. / Chen et al., 2022–2023.)
