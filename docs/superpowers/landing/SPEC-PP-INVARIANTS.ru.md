## 0. 30-секундная модель шва

При PP>1 + async scheduling (асинхронное планирование) один шаг декодирования
спекулятивного запроса разбит по рангам и по времени:

- **Последний ранг** запускает sampler (семплер) + **rejection oracle** (оракул отклонения),
  производя сетку `sampled_token_ids = [num_reqs, num_spec+1]` (валидные токены упакованы
  начиная с колонки 0, `-1` — padding после них). Он **broadcast**-ит эту сетку на
  остальные ранги и предлагает следующие черновики (drafts).
- **Не-последние ранги** никогда не запускают sampler. Они **получают** сетку и должны
  восстановить входные данные следующего шага (`input_ids`) из неё — потому что embedding
  (таблица вложений) живёт на первом ранге, и следующий токен должен быть заэмбеддирован
  *где-то*.
- **Scheduler** (планировщик) работает с опережением (async): резервирует spec-слоты
  с `-1` placeholders (заглушками), чтобы можно было запланировать шаг N+1 до того,
  как вернётся вывод шага N. Движок применяет этот вывод примерно через `pp_size−1`
  шагов (задержка `batch_queue`).

Всё, что может пойти не так, живёт в разрыве между «последний ранг знает настоящий
токен» и «каждый другой ранг, спустя k шагов, нуждается в этом настоящем токене для embedding».

## 2. Текущий фронт — break #2 (= инвариант I3), полная диагностика

**Состояние (session 6): Q16 ответ — НЕТ.** B1a (width-agnostic broadcast) + C3 (#40768
дисциплина scheduler-placeholder) оба сделаны и зелёные, но они **не** закрывают
break #2. Движок теперь доходит до `generate`, а затем не-последний ранг (rank0)
по-прежнему крашится при embedding `-1`.

**Корневая причина (решающая структурная находка).** При async PP **ни один путь кода
никогда не записывает настоящее значение сэмплированного токена в `token_ids_cpu`
не-последнего ранга.** Трейс:
- `_update_states` branch-1 (`gpu_model_runner.py:1342`): для async PP `new_token_ids ==
  []` → ничего не дописывает.
- branch-2 (`gpu_model_runner.py:1418`): продвигает счётчики и выставляет `is_token_ids = True`,
  но запись в `token_ids_cpu` стоит за `if new_token_ids:` → False для async PP → **значение
  не записывается**.
- receiver (`gpu_model_runner.py:4694`): записывает `-1` + счётчик, **без значения**.
- `_prepare_input_ids` (`gpu_model_runner.py:1707`): записывает только GPU `input_ids`
  (общий путь, колонка 0), но никогда не сохраняет в persistent `token_ids_cpu`.

Таким образом, настоящее значение живёт только транзиентно (GPU `input_ids` на общем
пути, один шаг в broadcast `recv`). `ngram_gpu` случайно заполняет через собственные
строки с `is_ngram_gpu`-gate + `update_ngram_gpu_tensors_incremental`; **у MTP нет
эквивалента** — break #2 является первым симптомом этого отсутствующего value-population.

**Исправление — C4:**
- **(A) value back-write** в receiver (`gpu_model_runner.py:4694`): записать подтверждённое
  значение из `recv` в `token_ids_cpu[i, pos]` вместо `-1`. (Необходимо.)
- **(B) возможно** однократное продвижение `num_tokens_no_spec` до `valid_count` — *или нет*:
  branch-2 (`:1418`) уже пересчитывает `num_tokens_no_spec` из `num_computed_tokens`,
  скорректированного методо-агностически (`:1487`), поэтому счётчик может уже самокорректироваться
  для MTP.

**Единственное, что чистым чтением не решить** — нужен ли (B): точная траектория
`num_tokens_no_spec` через k-шаговую задержку (branch-2's «advance to num_computed»
против receiver's «+1»). → **СЛЕДУЮЩЕЕ ДЕЙСТВИЕ — один целевой инструментальный прогон
на MiMo** (с env-gate, лог на каждом не-последнем шаге `{prev_index, num_computed_tokens,
num_tokens_no_spec pre/post branch-2 :1418 & receiver :4696, pos, recv row, valid_count}`),
который превращает (A)-only против (A+B) в данные. Затем реализовать C4 обоснованно,
TDD-написать чистый хелпер, если он выделяется в отдельный (стиль: `vllm/v1/worker/pp_spec_broadcast.py:21`),
MiMo greedy-equiv как оракул.

## 4. Оракул и зелёный пол (не регрессировать)

**Оракул корректности всегда один и тот же:** спекулятивный вывод **идентичен по токенам**
non-spec greedy той же модели. Никогда не принимайте «оно работает» за успех. Лестница:
1. **gloo CPU** — round-trip `pp_spec_broadcast.py` (без GPU).
2. **Scheduler unit tests** — учёт счётчиков через k-шаговую задержку (без GPU).
3. **MiMo-7B PP=2+MTP** на gpu-wb — быстрый оракул на настоящих весах (non-hybrid;
   чисто изолирует accounting). Загружается ~40 с.
4. **Qwen3.5-27B PP=2** vs `base.json` — финальный (hybrid; требует A1c int4 + `cpu_offload_gb=3`).

**Зелёный пол — эти тесты сделаны и должны оставаться зелёными** (прогоните перед любой
GPU-работой):
```bash
VIRTUAL_ENV="$(pwd)/.venv" .venv/bin/python -m pytest \
  tests/v1/core/test_async_scheduler.py tests/v1/spec_decode/test_pp_spec_broadcast.py -q
# тяжелее: tests/v1/core/test_scheduler.py → ожидается 101 passed
```
- **A1c** (память) — int4 draft embed, проверен на 27B. Самостоятельная ценность.
- **B1a** (ширина broadcast) — `pp_spec_broadcast.py`, протестирован gloo. Самостоятельная ценность.
- **C3** (дисциплина scheduler-placeholder ≈ #40768) — `test_async_scheduler` зелёный.
  Необходимое, но недостаточное условие для закрытия break #2; поставляется standalone.

## 5. Почему это не может «просто упроститься»

Очевидное упрощение — *«пусть не-последний ранг сам пересчитает токен»* —
не работает: у не-последнего ранга нет sampler-а и финальных logit-ов (они на последнем
ранге, по соглашению PP placement — `FOUNDATIONS.md` §4/§6). Токен *должен* передаваться
с последнего ранга, а в рамках pipeline — пережить k-шаговую задержку. Второе упрощение —
*«сделать это синхронным, чтобы не было placeholder-dance»* — тоже не работает: sync
MTP+PP **дедлочится** в текущем main (ранг ждёт spec-вывода, который никогда не приходит;
`PIPELINE-NARRATIVE.md` §Move 7). Так что сложность вынужденная: значение должно быть
*broadcast*-ировано (не пересчитано) и *сохранено* (не транзиентно), при *async* (не sync).
Value-back-write в C4 — минимальное выполнение этого требования. Более глубокая чистка —
типизированный `SampledTokenGrid`, делающий «valid-from-0, никогда не эмбеддировать `-1`»
невыразимо-неверным — это вклад C0/C1, который пенсионирует весь этот класс багов (`brick 81`).
