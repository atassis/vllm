Основы — из чего состоит LLM и зачем нужна каждая часть

Для кого этот документ. Для сильного software engineer'а, который не знаком с ML-внутренностями. Вы знаете, что такое токен, видели цепи Маркова и конечные автоматы, умеете читать матричную математику — но до сих пор потребляли AI, а не строили. Этот документ даёт ментальную модель, которую предполагают все остальные доки. После него PIPELINE-NARRATIVE.md (системная история) и PIPELINE.md (точная карта) встанут на место, потому что вы уже будете знать, что такое embedding / layer / head / KV cache, прежде чем читать, как vLLM их планирует и разбивает на страницы.

Лестница. FOUNDATIONS.md (этот — что представляет собой модель) → PIPELINE-NARRATIVE.md (почему система обслуживания устроена именно так) → PIPELINE.md (где всё живёт, file:line) → SPEC-PP-INVARIANTS.md (что нельзя ломать при изменениях).

Как читать. Нарратив, сверху вниз, с примерами. Математика подана интуитивно, но честно — там, где формула оправдывает своё место, она есть, с пояснением каждого термина. Якоря на код (file:line) приведены, чтобы вы сразу видели мостик от концепции к дереву vLLM, но открывать их при первом чтении не обязательно.

0. Начнём с того, что вы уже знаете: цепь Маркова

Вы знаете цепь Маркова: вы в каком-то состоянии, и фиксированная таблица вероятностей говорит, каким будет следующее состояние. «Погода завтра зависит только от погоды сегодня.»

LLM — та же форма, но с тремя улучшениями:

  1. «Состояние» — это весь текст до текущего момента, в виде последовательности токенов, а не только последний символ. (Так что это очень высокопорядковая цепь Маркова.)
  2. Вероятности переходов не хранятся в таблице — они вычисляются большой обученной функцией (нейронной сетью). Таблица для «всех возможных текстов» была бы бесконечной; сеть сжимает её в ~миллиарды чисел (веса).
  3. Результат — распределение вероятностей по следующему токену, из которого вы выбираете один, добавляете его и повторяете.

Этот цикл — вся игра:

tokens so far  ─▶  model  ─▶  probability over the next token  ─▶  pick one  ─▶  append
       ▲                                                                          │
       └──────────────────────────────────────────────────────────────────────────┘

Это называется авторегрессией ("регрессия по собственному прошлому выводу"). Всё остальное в этом документе — embeddings (эмбеддинги), attention (внимание), KV cache, head — это просто то, что находится внутри блока «model», а всё в доках vLLM — о том, как выполнять этот цикл для тысяч последовательностей одновременно, быстро, при ограниченной GPU-памяти, не портя вывод.

Запомните одно число: типичная модель за один проход производит один токен. Этот единственный факт обусловливает почти каждое дизайнерское решение дальше (именно поэтому decode медленный, именно поэтому KV кэш существует, именно поэтому speculative decoding того стоит).

1. Токены → эмбеддинги: превращаем символы в геометрию

Токенизация. Текст сначала разбивается на токены — подсловные куски, каждый с целочисленным id. "unhappiness" может стать ["un", "happ", "iness"] → [1023, 5519, 8841]. Словарь фиксирован (например, 250 000 токенов для Qwen3.5). Думайте о token id как о «номере строки».

Почему нельзя подавать id напрямую. Id 5519 — просто индекс, в нём нет смысла. 5519 не «больше» и не «ближе к» 5520 в каком-либо полезном смысле. Сети нужен смысл, выраженный через геометрию: похожие токены должны быть близкими точками в пространстве, чтобы математика (скалярные произведения, суммы) могла оперировать смыслом.

Эмбеддинг — это таблица поиска. Это матрица размера [vocab_size, hidden_size] — по одной строке на токен, каждая строка — вектор из hidden_size чисел с плавающей точкой (например, 5120). «Заэмбеддить токен 5519» буквально означает «взять строку 5519». Эти строки обучены во время тренировки так, чтобы, например, векторы для «king» и «queen» оказались связаны.

token id 5519  ──lookup──▶  [0.21, -1.03, 0.44, … , 0.07]   (a 5120-dim vector)
                            └──────── this token's "meaning vector" ────────┘

Почему это важно для vLLM (мостик). Эта таблица огромна: 250k × 5120 × 2 байта ≈ 2.4 ГБ только для эмбеддинга. В vLLM это VocabParallelEmbedding (vllm/model_executor/layers/vocab_parallel_embedding.py:192). Когда вы читаете в заметках проекта, что «A1c квантует эмбеддинг черновой модели до int4», теперь вы точно знаете, что именно сжимается и почему это даёт ~1.8 ГБ — это именно эта таблица, продублированная для speculative draft-модели. (И квантование безопасно — почему, мы увидим в §7.)

На выходе этого этапа последовательность превращается в стек векторов: [num_tokens, hidden_size]. Этот блок чисел называется hidden states (скрытые состояния) — рабочее представление текста в модели. Оно будет трансформироваться слой за слоем.

2. Слои (transformer blocks): где происходит «мышление»

Модель — это стек одинаковых блоков (например, 64 штуки). Каждый блок принимает hidden states и выдаёт уточнённые hidden states той же формы. Укладка в стек позволяет модели строить всё более абстрактные представления — ранние слои ≈ синтаксис, поздние слои ≈ смысл/задача (грубо).

Каждый блок делает два дела:

2a. Attention (внимание) — смешиваем информацию между токенами

Это сердце transformer'а, и единственная концепция, на которой стоит притормозить.

До сих пор вектор каждого токена знал только о себе самом. Но «it» в «the cat sat because it was tired» нужно оглянуться назад и найти «cat». Attention — это механизм, с помощью которого токен может посмотреть на предыдущие токены и взять взвешенную смесь их информации.

Для каждого токена блок вычисляет три вектора из его hidden state через обученные матрицы:

  • Query (Q) — «что я ищу?»
  • Key (K) — «что я предлагаю, как то, на что могут смотреть?»
  • Value (V) — «фактическая информация, которую я отдам, если на меня обратят внимание».

Затем, для токена i:

  1. Сравниваем его Q с K каждого предыдущего токена (скалярное произведение) → оценка релевантности для каждого прошлого токена. Высокая оценка = «этот токен мне релевантен».
  2. Softmax этих оценок → веса, сумма которых равна 1.
  3. Выход = взвешенная сумма векторов V прошлых токенов.

В одну строку (знаменитая формула), для всей последовательности сразу:

Attention(Q, K, V) = softmax( Q·Kᵀ / √d ) · V
  • Q·Kᵀ — запрос каждого токена, умноженный скалярно на ключ каждого токена → сетка [n × n] оценок релевантности.
  • / √d — масштабирование, чтобы softmax не насыщался (d = размерность head'а). Техническая деталь.
  • softmax(...) — превращает каждую строку оценок в веса с суммой 1.
  • · V — смешивает значения с этими весами.

Каузальная маскировка. Токен может смотреть только назад (нельзя смотреть на слова, которые ещё не сгенерированы). Поэтому верхний треугольник сетки [n × n] маскируется в ноль. Именно поэтому это называется «causal self-attention».

Heads (головы). Всё это выполняется параллельно несколькими attention heads, каждый со своими матрицами Q/K/V, так что разные головы могут специализироваться («одна отслеживает подлежащее, другая — позиции»). Их выходы конкатенируются. Это и есть «multi-head» в «multi-head attention».

2b. MLP / feed-forward — трансформируем каждый токен

После того как attention перемешал информацию между токенами, маленькая двухслойная нейронная сеть (MLP или feed-forward блок) применяется к вектору каждого токена независимо — «теперь, когда ты собрал контекст, улучши себя». Здесь живёт большая доля параметров.

2c. Сантехника, делающая глубокие стеки обучаемыми

  • Residual connections: каждый блок добавляет свой выход к своему входу (x + block(x)) вместо того, чтобы заменять — так информация и градиенты проходят через 64 слоя, не исчезая. (Именно этот residual вы увидите, путешествующим между PP-стадиями.)
  • Нормализация (RMSNorm/LayerNorm): перемасштабирует векторы, чтобы числа оставались стабильными.

Мостик. В vLLM пара {hidden_states, residual} на каждый токен — это именно то, что пересекает границу pipeline-parallel стадии (vllm/sequence.py:12, IntermediateTensors) — теперь вы знаете, что это просто «рабочее представление, в середине стека, переданное GPU, который хранит следующие слои».

3. KV cache — самая важная системная идея, и почему

Это концепция, которая объясняет 80% машинерии памяти vLLM. Поймите её — и остальные доки откроются.

Проблема. Чтобы сгенерировать токен N+1, attention (§2a) нужны K и V каждого предыдущего токена, на каждом слое. Если пересчитывать K и V для всего префикса на каждом шаге, генерация ответа из 1000 токенов обошлась бы в ~1000× больше работы attention — O(n²) суммарно. Мучительно медленно.

Инсайт. K и V прошлого токена никогда не меняются после вычисления. Ключ токена 5 — это ключ токена 5 навсегда. Поэтому вычислите их один раз и закешируйте. На каждом новом шаге новый токен вычисляет только свои Q, K, V, добавляет K/V в кэш и обращает свой Q к всему закешированному K/V.

step N:   new token computes Q,K,V  →  append K,V to cache  →  attend Q over ALL cached K,V
                                          (cache grows by 1 token × every layer)

Таким образом decode становится O(1) пересчёта за шаг — но ценой: нужно хранить K и V для каждого токена × каждого слоя × каждого attention head'а. Это хранилище — KV cache, и для длинных последовательностей он доминирует в GPU-памяти — больше, чем веса модели.

Теперь каждое решение vLLM о памяти очевидно:

  • KV cache огромен и привязан к запросу → нельзя давать каждому запросу буфер фиксированного максимального размера (расточительство + фрагментация) → PagedAttention хранит его в фиксированных блоках с block table на каждый запрос, как виртуальная память ОС. (PIPELINE.md §7.)
  • Блоки могут закончиться посреди шага → планировщик должен вытеснять (preempt) запросы.
  • Идентичные префиксы (одинаковый system prompt) могут разделять блоки → prefix caching.
  • Speculative draft имеет свои собственные K/V (собственный attention layer), но разделяет block tables — это и есть тема brick 30.

Число, чтобы прочувствовать масштаб: для 7B-модели при нескольких тысячах токенов контекста KV cache часто занимает несколько ГБ на каждый конкурентный запрос. На GPU с 16 ГБ «сколько KV-блоков влезет» и есть «сколько запросов я могу обслуживать одновременно». Вот почему worker выполняет профилирующий проход для определения размера num_gpu_blocks (PIPELINE.md §7) раньше всего остального.

4. Head и logits — превращаем вектор обратно в токен

После последнего блока каждая позиция имеет финальный вектор hidden state — полностью готовое представление модели о том, «что идёт следующим». Чтобы превратить это в настоящий токен, нужен ещё один шаг.

LM head — это матрица размера [hidden_size, vocab_size]. Умножение финального вектора hidden state на неё даёт одну оценку для каждого токена словаря — logits (логиты):

final hidden vector  ──LM head ([hidden × vocab])──▶  logits = [score per token, ×250k]
  • Logits — сырые, неограниченные оценки. softmax(logits) превращает их в распределение вероятностей по словарю.
  • Сэмплирование выбирает фактический следующий токен: - Greedy / argmax — берём токен с наибольшим logit. Детерминировано. - Temperature / top-p / top-k — сглаживают или ограничивают распределение и сэмплируют случайно, ради разнообразия.

Два мостика, которые пригодятся позже:

  1. LM head часто привязан к таблице эмбеддингов (те же веса, транспонированные) — одна матрица делает «id → вектор» на входе и «вектор → оценки» на выходе. (Именно поэтому в заметках проекта говорится, что draft «разделяет lm_head таргет-модели».)
  2. Детерминированность argmax — это крючок, на котором держится корректность speculative decoding (§7): жадный вывод — фиксированная функция от logits, поэтому токен черновика «правильный» тогда и только тогда, когда он равен argmax таргета.

В vLLM это compute_logits + сэмплер; head живёт только на последней pipeline-стадии (эмбеддинг — только на первой) — что, теперь, когда вы знаете, что каждый из них делает, является естественным местом для них.

5. Один полный проход, от начала до конца

Собрав §1–§4 вместе, вот один forward pass, производящий один токен:

token ids
   │  §1 embedding lookup            [n, hidden]
   ▼
 ┌─────────────────────────────────────────────┐
 │  block 1:  attention (over KV cache) + MLP   │  §2
 │  block 2:  …                                 │
 │   …  (×64)                                    │
 └─────────────────────────────────────────────┘
   │  final norm                     [n, hidden]
   ▼
   §4 LM head → logits [n, vocab]  →  take the LAST position's logits
   ▼
   sample (argmax / temperature)  →  next token id
   ▼
   append to the sequence, write this step's K/V into the cache, and loop  (§0, §3)

Это полная языковая модель. Prefill (предзаполнение) = прогнать всё это через весь промпт сразу (заполняет KV cache для всех токенов промпта, производит первый новый токен). Decode (декодирование) = прогонять по одному токену за раз (каждый шаг добавляет один K/V в кэш). Планировщик vLLM намеренно стирает различие prefill/decode — он просто отслеживает «сколько токенов этого запроса уже вычислено» — это идея «без фаз» из PIPELINE-NARRATIVE.md §Move 1/3.

Почему decode медленный (и почему нам не всё равно). В decode вы прокачиваете все веса и весь KV cache через GPU, чтобы произвести один токен. Вычислительные блоки GPU в основном простаивают, ожидая данных из памяти — decode ограничен пропускной способностью памяти (memory-bandwidth-bound), а не вычислениями. Этот единственный факт является всей мотивацией для следующих двух разделов.

6. Pipeline parallelism в одном абзаце (вы это уже понимаете)

Модель (§2) — стек слоёв. Если она не помещается на одну GPU, разделите стек: GPU0 хранит слои 0–k (и эмбеддинг, §1), GPU1 хранит слои k–end (и head, §4). Hidden state токена течёт GPU0 → GPU1 один раз на каждой границе (IntermediateTensors из §2c). Это pipeline parallelism (PP). Альтернатива — tensor parallelism — делит каждый слой и должна синхронизироваться на каждом слое: нормально поверх быстрого NVLink, смертельно поверх медленного PCIe. Полная история: PIPELINE-NARRATIVE.md §Move 4. Единственное, что нужно вынести отсюда: при PP эмбеддинг находится на первой GPU, head — на последней, а speculative draft (следующий раздел) естественно живёт на последней GPU, потому что именно там уже находится финальный hidden state.

7. Speculative decoding и MTP — наконец, проект в контексте

Теперь та часть, о которой весь проект.

Возможность. Decode ограничен памятью (§5): производство одного токена едва использует вычислительную мощь GPU. Итак — можем ли мы проверить несколько кандидатных токенов почти за ту же цену, что и один? Если у нас уже есть угадка для нескольких следующих токенов, таргет-модель может верифицировать их все за один forward pass (attention по тому же KV cache, просто чуть больше позиций — почти бесплатно на GPU, ограниченном памятью).

Загвоздка. Нельзя знать токен N+1 до того, как произведён токен N — это авторегрессия (§0). Поэтому нужен дешёвый угадчик («черновик», draft) и способ верифицировать его угадки, не меняя результат.

Черновик (drafter). Существует несколько видов (n-gram, EAGLE, draft-model), но наш — это MTP = Multi-Token Prediction. Обычная модель предсказывает один следующий токен из финального hidden state (§4). MTP прикручивает маленький дополнительный модуль — свой маленький эмбеддинг + один дополнительный transformer layer + разделяемый head, — который, получив тот же финальный hidden state, что только что произвела таргет-модель, предсказывает токен после следующего. Потому что:

  • его входные данные (hidden state таргета) уже вычислены → бесплатно,
  • он крошечный (один слой) → дёшево,
  • он обучен имитировать таргет → его угадки часто правильны (~71% принято на llama.cpp),

он — отличный генератор черновиков. В vLLM это модель вроде vllm/model_executor/models/qwen3_5_mtp.py. Теперь вы можете читать brick 20 («у черновика есть свой эмбеддинг») и brick 30 («черновик переиспользует hidden state таргета, живущий на последнем ранге») — и они будут значить что-то конкретное.

Верификация (почему это доказуемо корректно). Rejection sampler — это оракул. В жадном режиме правило таково:

токен черновика принимается тогда и только тогда, когда он равен argmax таргет-модели на этой позиции; иначе он заменяется на argmax таргета, а все последующие черновики выбрасываются.

Пройдитесь по тому, почему это идентично обычному жадному декодированию: обычное жадное выдало бы argmax таргета на каждой позиции. Если черновик угадал правильно — отлично, мы пропустили его пересчёт. Если черновик угадал неверно — подставляем правильный argmax, поэтому выданный токен всё равно в точности тот, что выдало бы жадное. Черновик только сохраняет работу; он никогда не может изменить ответ. (vllm/v1/sample/rejection_sampler.py:708 и :452.)

Два следствия, которые движут проектом:

  1. Агностицизм к весам. Поскольку корректность зависит только от (argmax таргета, угадка черновика), качество черновика меняет только частоту принятия — никогда не меняет вывод. Это лицензия делать черновик lossy (с потерями): квантование 2.4 ГБ эмбеддинга черновика до int4 (A1c) может только снизить acceptance, никогда не испортит текст. Именно поэтому dummy/MiMo-веса валидны для тестирования механики.
  2. Бонусный токен и сетка. Если все K черновиков приняты, таргет даёт ещё один «бесплатный» токен (он всё равно вычислил те logits). Поэтому вывод сэмплера — это сетка [num_reqs, num_spec+1], валидные токены упакованы слева, заполнение -1 справа. Этот -1 и переменная ширина — именно то, что должно корректно пережить пайплайн — это баги, которые фиксирует проект (PIPELINE-NARRATIVE.md §Move 7).

Почему «spec × PP × async» сложно (формулировка в одном предложении, которое вы теперь можете разобрать): черновик производится на последней GPU, но более ранним GPU нужны результирующие токены, чтобы построить вход следующего шага; а поскольку движок пайплайнит pp_size шагов вперёд, бухгалтерия черновиков на каждом шаге (те самые placeholder'ы -1) должна оставаться корректной через задержку в несколько шагов. Вот где шов.

8. Компактный математический букварь

Ровно столько, чтобы следить за статьями и рассуждать вслух — линейная алгебра у вас уже есть.

  • Всё — matmul. Hidden states — это матрица [n_tokens, hidden]. Линейный слой — X·W. Attention и MLP — стеки таких операций. «В модели N миллиардов параметров» = суммарный размер всех матриц W.
  • logits → вероятности. softmax(z)_i = e^{z_i} / Σ_j e^{z_j} — потенцируем и нормируем, чтобы оценки стали распределением. argmax берёт наибольший; температура T делит logits на T перед softmax (T<1 заостряет → более детерминированно, T>1 сглаживает → более случайно); top-p оставляет только наименьший набор токенов, чьи вероятности дают в сумме p.
  • attention softmax(QKᵀ/√d)·V — §2a, термин за термином. QKᵀ — это [n, n] (каждый токен против каждого), вот почему длинные контексты дорогие и почему KV cache (кеширующий K, V) — ключевая оптимизация.
  • compute-bound vs memory-bound. Prefill обрабатывает много токенов сразу → много matmul на каждый загруженный байт → compute-bound. Decode обрабатывает один токен, но должен перезагрузить все веса + KV → мало matmul на байт → memory-bound. Speculative decoding эксплуатирует именно это: дополнительные кандидатные токены почти бесплатны на шаге, ограниченном памятью.
  • почему rejection sampling точен (случай без жадности, для полноты картины): чтобы сэмплировать из целевого распределения p, предлагая из черновика q, принимаем токен черновика x с вероятностью min(1, p(x)/q(x)), а при отклонении сэмплируем из нормированной положительной части p−q. Математика гарантирует, что финальные сэмплы распределены в точности как при выборке из p. Жадный (§7) — вырожденный случай, когда p — пик на argmax, что сводится к «принять тогда и только тогда, когда равны.» (Статьи: Leviathan et al. / Chen et al., 2022–2023.)

Как читать этот документ. PIPELINE.md — это карта: что представляет собой каждый компонент и где он находится (file:line). Читайте сверху вниз; документ рассчитан на опытного инженера, который ни разу не открывал дерево исходников vLLM.

Вся архитектура — это одна проблема и цепочка вынужденных ходов. Здесь почти нет ничего надуманного — каждая часть есть цена за решение проблемы, порождённой предыдущей. Те немногие места, которые действительно надуманны, честно названы в конце (Часть 4): именно контраст делает всё остальное убедительным. Часть 0 — Одна проблема

Обслуживать множество одновременных LLM-запросов на скудной, дорогой памяти GPU — с малой задержкой и высокой пропускной способностью — никогда не искажая вывод.

Удержите в голове пять ограничений: множество, скудная память, малая задержка, высокая пропускная способность, точная корректность. Каждый компонент ниже — вынужденный ход из напряжения между ними. Пройдём по цепочке: каждый ход снимает одно давление и порождает следующее.

autoregression → batch them → continuous batching → paged KV → chunked prefill
   → model too big → pipeline parallelism → pipeline bubble → batch_queue
   → decode is memory-bound → speculative decoding → spec × PP × async = our seam

Часть 1 — Цепочка вынужденных ходов

Ход 1 — От «одного запроса за раз» к continuous batching (непрерывной пакетной обработке)

Давление. GPU — это машина для работы с высокой пропускной способностью: она хочет перемножать большие матрицы, а не поток крошечных. Но текст генерируется авторегрессивно — один токен за один forward pass, каждый зависит от предыдущего. Один запрос в одиночестве занимает лишь ничтожную долю GPU.

Наивный ход. Собрать фиксированный batch из N запросов, гнать их синхронно до завершения всех, затем взять следующие N.

Где ломается. Запросы завершаются в разное время и имеют разную длину. Фиксированный batch простаивает на каждом слоте, чей запрос уже закончился, и не может принять новый запрос до тех пор, пока весь batch не вычерпается. Задержка и утилизация вместе рушатся под реальным трафиком.

Что делает vLLM. Continuous batching: никакого объекта batch вообще не существует. На каждом шаге планировщик заново выводит текущее множество запросов — завершённые выбывают, ожидающие вступают — из бюджета токенов. Собственный комментарий планировщика — самая ёмкая строка в кодовой базе: нет фазы prefill и нет фазы decode; у каждого запроса есть только num_computed_tokens и num_tokens_with_spec, и каждый шаг назначает токены так, чтобы первое догоняло второе. vllm/v1/core/sched/scheduler.py:336

Новая цена, которую это создаёт. Если batch теперь текучий, то входные данные модели (идентификаторы токенов, позиции, block tables) меняются на каждом шаге. Перестраивать эти тензоры с нуля каждый шаг сожгло бы CPU. → вынуждает persistent batch из Хода 5. А смешивание промпта на 32k токенов с однотокенными decode-шагами в одном бюджете задушило бы задержку decode → вынуждает chunked prefill (следующий ход).

Ход 2 — От «непрерывного KV-буфера» к PagedAttention

Давление. KV cache (ключи/значения attention для каждого прошлого токена) растёт на один слот за токен на каждом слое и быстро поглощает память GPU — значительно больше, чем веса модели при длинных последовательностях.

Наивный ход. Выдать каждому запросу непрерывный KV-буфер размером max_model_len.

Где ломается. Итоговая длина запроса неизвестна заранее, поэтому резервируется максимум — а большинство запросов коротки, и огромное количество зарезервированной памяти уходит впустую. Хуже того, непрерывные буферы на каждый запрос не могут ничего разделять: два запроса с одинаковым системным промптом платят за него дважды. Фрагментация памяти добивает окончательно.

Что делает vLLM. PagedAttention — заимствует трюк виртуальной памяти ОС. KV хранится в блоках (blocks) фиксированного размера; block table на запрос отображает логический блок → физический идентификатор блока, а slot mapping на токен задаёт каждому токену его физический слот. Блоки выделяются по требованию и подсчитываются с помощью reference counting. vllm/v1/worker/block_table.py:70

Новая цена, которую это создаёт. Теперь выделение блока может завершиться неудачей в середине шага (нет свободных блоков) — а значит, планировщику нужен способ вытеснить (preempt) работающий запрос и освободить его блоки (путь allocate_slots → None → preempt). А для разделяемых блоков нужен хеш-индекс, чтобы их можно было найти → prefix caching. vllm/v1/core/kv_cache_manager.py:238

Ход 3 — От «prefill = decode» к chunked prefill + prefix caching

Давление. Промпты могут содержать десятки тысяч токенов; шаг decode — один токен. Они используют один и тот же forward pass и один и тот же бюджет токенов.

Наивный ход. Когда поступает промпт, обработать его целиком за один шаг.

Где ломается. Один prefill на 32k токенов монополизирует шаг, и decode всех остальных запросов стоит за ним — возникает резкий скачок задержки. Повторный prefill уже вычисленного префикса (тот же системный промпт, повторные попытки) расходует самую дорогостоящую часть работы.

Что делает vLLM. Поскольку планировщик думает только в терминах «догнать num_computed_tokens», chunked prefill достаётся почти бесплатно: достаточно ограничить num_new_tokens остатком бюджета токенов — и длинный промпт потребляется за несколько шагов, пока decode-шаги продолжают поступать. Prefix caching ищет уже закешированный наидлиннейший префикс блоков по хешу и пропускает его вычисление (пересчитывается только последний токен для получения logits). vllm/v1/core/sched/scheduler.py:~675, vllm/v1/core/kv_cache_manager.py:196

Новая цена, которую это создаёт. Структурно — никакой: здесь дизайн «без фаз» окупается. Chunked prefill — следствие модели бюджетов, а не новая подсистема. Счёт придёт в другом месте: модель всё ещё должна влезть.

Ход 4 — От «одного GPU» к pipeline parallelism (PP) (не TP, и это важно)

Давление. Модель не влезает на один GPU. Наше железо — два потребительских GPU на PCIe без NVLink — медленный канал.

Наивный ход. Tensor parallelism (TP): разделить веса каждого слоя между обоими GPU и объединить частичные результаты.

Где ломается. TP выполняет all-reduce активаций на каждом слое. По быстрому NVLink — нормально; по PCIe — гибель: канал насыщается, и GPU проводит время в ожидании друг друга, а не в вычислениях.

Что делает vLLM. Pipeline parallelism: разделить слои модели на последовательные стадии (rank0 = слои 0..k, rank1 = слои k..L). Через границу стадии передаётся совсем немного — словарь {hidden_states, residual} на токен (IntermediateTensors), один point-to-point per boundary, а не all-reduce на каждый слой. Именно поэтому PP, а не TP — правильный инструмент для пары без NVLink. vllm/distributed/utils.py:109, vllm/sequence.py:12

Новая цена, которую это создаёт. В конвейере возникают пузыри (bubbles): пока rank0 вычисляет стадию 1 батча B, rank1 не имеет работы до прихода активаций B — и наоборот. Наивный цикл оставлял бы каждый GPU простаивающим половину времени. → вынуждает Ход 5.

Отступление — соглашение о размещении, с которым борется работа по spec. В PP embedding живёт на первом ранге, а norm/lm_head — на *последнем; отсутствующие слои — PPMissingLayer-заглушки. Канонический forward: if first: embed; elif not last: read intermediate tensors; ... ; if last: norm. Драфтер MTP работает на *последнем* ранге, где is_first_rank` равно False — поэтому без флага «standalone draft» он попал бы в ветку чтения промежуточных тензоров и никогда не выполнил бы embed. Этот единственный флаг — вся модельная часть изменений Design C. (Кирпичи 10/20/60.)

Ход 5 — От «синхронного шага» к batch_queue (и persistent batch)

Давление. Пузыри PP. Вы платите за N GPU и, при синхронном цикле, используете ~1/N из них.

Наивный ход. Оставить простой цикл: schedule → run → apply → repeat. (Именно так работает step(), и это корректно — vllm/v1/engine/core.py:443.)

Где ломается. Простой цикл ждёт завершения батча B перед планированием следующего, поэтому занята всегда лишь одна стадия конвейера. Весь смысл PP выбрасывается.

Что делает vLLM. step_with_batch_queue: держать pp_size батчей в полёте в deque(maxlen=pp_size). Запланировать шаг N, запустить его неблокирующим образом, добавить в очередь и вернуться, не ожидая, пока есть место; как только очередь заполнится — извлечь старейший и применить его. Теперь на каждой стадии всегда есть работа. vllm/v1/engine/core.py:484, vllm/config/vllm.py:497

Новая цена, которую это создаёт — и обе стоимости принципиальны для нас:

  1. Задержка в k шагов. Результат батча B применяется приблизительно через pp_size−1 шагов после его планирования. Удерживаемый SchedulerOutput — это устаревший снимок: spec-токены, плейсхолдеры и флаги prefill могут измениться за это время. Любое состояние на шаг теперь обязано корректно пережить эту задержку.
  2. Persistent batch. Поскольку входные данные меняются на каждом шаге (Ход 1), но перестраивать тензоры накладно, InputBatch хранит CPU-буферы между шагами, а _update_states согласует их; после удалений condense() уплотняет буферы. Это уплотнение затем должно перестраивать индексные таблицы — и при задержке в k шагов это опасность устаревшего маппинга (слабое место W6). vllm/v1/worker/gpu_input_batch.py:91, :683

Ход 6 — От «одного токена за forward» к speculative decoding (спекулятивному декодированию)

Давление. Decode ограничен памятью: каждый шаг прогоняет весь KV cache и все веса через GPU, чтобы выдать один токен. Вычислительные блоки в основном простаивают — GPU мог бы верифицировать несколько токенов за примерно тот же трафик памяти.

Наивный ход. Просто генерировать больше токенов за шаг. Но нельзя — токен N+1 зависит от токена N, который ещё не создан.

Где ломается очевидная спекулятивная идея. Пусть дешёвая «draft»-модель предугадывает следующие K токенов, а целевая модель проверяет их. Опасность: если просто принять догадки драфтера, распределение вывода изменится — тихая деградация качества (класс ошибки «бессмыслица»). Корректность не бесплатна.

Что делает vLLM. Speculative decoding с rejection sampler (выборкой с отклонением) в роли оракула корректности. Драфтер (ngram / EAGLE / MTP / draft-model) предлагает K токенов; целевая модель верифицирует их за один forward. В жадном режиме правило точное: draft-токен принимается тогда и только тогда, когда он совпадает с argmax целевой модели; иначе он заменяется этим argmax, а остальные отклоняются. Таким образом, вывод — это чистая функция от (target argmax, draft sequence) — доказуемо идентичная нежёсткому жадному декодированию независимо от качества драфтера. Драфтер меняет лишь acceptance rate (долю принятых токенов), но никогда — результат. vllm/v1/sample/rejection_sampler.py:708, :452

Элегантное следствие (и почему A1c безопасен). Поскольку корректность не зависит от весов, вам разрешено делать драфтер lossy (с потерями). Это лицензия, стоящая за A1c: квантование embedding словаря драфтера до int4 может лишь снизить acceptance rate, но никогда не испортит вывод. Это также означает, что dummy/MiMo-веса являются допустимыми оракулами для тестирования механизма — реальные 27B не нужны, чтобы доказать корректность каскада. (Кирпич 70.)

Новая цена, которую это создаёт. Сэмплер теперь выдаёт сетку переменной ширины [num_reqs, num_spec+1] (принятые драфт-токены + один «бонусный» токен, если все K приняты), дополненную -1. Этот сторожевой -1 и переменное количество принятых токенов теперь должны корректно проходить через всё остальное — в том числе через k-шаговую задержку PP. → Ход 7.

Ход 7 — Совмещение spec × PP × async (это наш шов)

Давление. Все три оптимизации одновременно: драфтер работает только на последней стадии PP (там, где резидентно скрытое состояние цели — ноль лишнего PCIe-трафика), но более ранним стадиям нужны сэмплированные токены для построения следующего входа. И при batch_queue всё это задержано на k шагов.

Наивный ход. Транслировать сэмплированные токены последнего ранга на остальные; позволить планировщику оптимистично резервировать spec-слоты с плейсхолдерами -1, чтобы продолжать планирование вперёд.

Где ломается. В двух точках — точно:

  1. Broadcast был жёстко закодирован на ширину [num_reqs, 1] — нормально без spec, неверно для MTP с [num_reqs, num_spec+1]. (Исправлено: B1a, новый width-agnostic vllm/v1/worker/pp_spec_broadcast.py.)
  2. Плейсхолдер -1 заполняется только на «общем» (common) пути. Когда запрос попадает на «нестандартный» путь (на этом шаге драфты не запланированы), не-последний ранг читает -1 прямо в embedding lookup → out-of-bounds crash (break #2). Корневая причина — upstream PR #40768 («stale async placeholder tokens», исправляет #37159), дисциплина на стороне планировщика: эмитировать -1 только тогда, когда запрос действительно был запланирован на предыдущем шаге.

Что это говорит об архитектуре. Путь spec-under-PP работает для ngram_gpu (его логические вентили — is_ngram_gpu), но так и не был доделан для MTP — абстракция никогда не обобщалась дальше одного пропозера, под который и была написана (слабое место W5). В этом вся задача: сделать этот шов корректным и типизированным для MTP. (Кирпичи 40/80/81.)

Часть 2 — Сквозные ходы (не на магистрали, но вынужденные)

Почему три уровня процессов, а не одна большая программа? Три независимых давления:

  • Изоляция — CUDA OOM в модели не должна убивать API-сервер. Поэтому логика движка работает в собственном процессе (EngineCoreProc), за ZMQ.
  • Перекрытие — сериализация и socket I/O не должны блокировать горячий цикл. Поэтому ввод и вывод получают каждый свой daemon-поток, а горячий цикл всегда делает только put_nowait.
  • Дистрибуция — репликам data-parallel нужен координатор. Поэтому существует процесс DP broker.

Чистая часть: логика (EngineCore) отделима от транспорта. InprocClient запускает ту же самую логику in-process для офлайн-использования; MP-клиенты помещают её за сокеты. Единственная цена — «движок» размазан по трём именам классов (EngineCore / EngineCoreProc / EngineCoreClient). vllm/v1/engine/core.py:95

Почему «async» встречается трижды? AsyncLLM (asyncio-фронтенд), async_scheduling (перекрытие schedule и execute через плейсхолдеры -1 в движке) и AsyncGPUModelRunnerOutput (перекрытие копии device→host) — три независимые вещи, которым случилось разделить одно слово. Ни одна из них не является другой. Это опасность в именовании, а не проблема проектирования — но именно это чаще всего приводит к неправильному прочтению кода.

Почему здесь важны статические типы. vLLM запускает mypy в CI, поэтому Final / Protocol / TypedDict / NewType — единственные «контракты времени сборки», которые предлагает язык. Область spec-under-PP сломалась для MTP отчасти именно из-за их отсутствия: сторожевой -1 — голый литерал, изобретённый в трёх местах; сетка [num_reqs, num_spec+1] имеет форму и расположение только в комментариях; поверхность proposer — цепочки isinstance вместо Protocol. (Кирпич 81.)

Часть 3 — Где сложность не вынужденная (честная часть)

Это контраст, который делает всё остальное убедительным. Не всё здесь — вынужденный ход; часть накоплена. Назвать это вслух — значит сохранить честность повествования.

  • gpu_model_runner.py — god object на 7 583 строки (W1). Forward, attention, sampling, spec, PP, multimodal, pooling, cudagraphs, профилирование — всё в одном классе, с ветками is_last_rank / is_ngram_gpu / use_async_spec_decode, перемежёнными по всему коду. Это не вынужденный ход; именно так выглядит результат, когда каждая фича приземляется в один и тот же файл. Чистый дизайн выделил бы SpecDecodeFlow / SamplingFlow / PPTransport за типизированные интерфейсы. vllm/v1/worker/gpu_model_runner.py:422
  • Нет владельца у машины состояний запроса (W2). request.status = … и счётчики токенов мутируются из множества мест планировщика; FSM неявна, и нет даже assert num_rejected ≤ num_computed_tokens. Чистый дизайн имел бы одного владельца с охраняемыми переходами.
  • Сторожевой -1 повсюду (W3). Эмитируется и планировщиком, и runner-ом, заполняется только на обычном пути → утечка break #2. Это единственная правка с наибольшим рычагом, и именно тот же пробел породил слабости типизации: типизированный SampledTokenGrid закрыл бы оба.

Закономерность: вынужденная сложность (paging, continuous batching, PP, batch_queue, rejection oracle) — существенна и элегантна. Накопленная сложность (god object, неявная FSM, разбросанные -1) — это именно там, где живут баги, и именно то, что укрепляет наш вклад (A1c, B1a, а затем типизированный контракт C0/C1).

Часть 4 — Наше изменение как часть истории

Путь, которого мы касаемся, тонкий, но лежит поверх всех шести предыдущих ходов. Пройдём ещё раз, быстро: запрос группируется в batch (1), его KV разбивается на страницы (2), его длинный промпт разбивается на чанки (3), модель разделена по стадиям PP (4), движок конвейеризирует её с задержкой k шагов (5), и speculative decoding предлагает K токенов, которые rejection oracle верифицирует (6). Наш шов (7) — это место, где состояние spec из хода 6 должно пережить задержку из хода 5 через границу стадии из хода 4.

Конкретно: memory wall решён (A1c — int4 draft embed при загрузке, лицензировано weight-agnostic оракулом), транспорт исправлен (B1a — width-agnostic broadcast), и оставшийся вентиль — break #2 = upstream #40768, при этом более глубокая правка — типизированный контракт для spec-token grid (C0/C1), который одним разом снял бы слабые места W3/W4/W5. Изменение на стороне модели крошечное (один флаг standalone-draft); основная часть и риск — это обвязка корректности, что и объясняет, почему необходимо понять вынужденную форму конвейера прежде чем что-то в нём менять. 1.2 Границы процессов и потоков

  • Frontend-процесс. AsyncLLM/LLMEngine + Processor + OutputProcessor + EngineCoreClient. В AsyncLLM цикл asyncio; сторона вывода работает как фоновая asyncio-задача _run_output_handler (async_llm.py). В SyncMPClient сторона вывода — это демон-поток, опрашивающий ZMQ-сокет (core_client.py).
  • EngineCore-процесс (EngineCoreProc). (core.py:~1264), поэтому цикл никогда не блокируется на сериализации вывода.
  • Worker-процесс(ы), по одному на каждый глобальный ранг под MultiprocExecutor. Каждый запускает Worker, оборачивающий GPUModelRunner; исполнитель диспатчит execute_model через collective_rpc поверх очередей сообщений.

Разделение между логикой (EngineCore) и транспортом (EngineCoreProc + EngineCoreClient) — самый чёткий шов в системе: InprocClient запускает EngineCore непосредственно in-process для офлайн-использования, тогда как MP-клиенты помещают его за ZMQ.   • RUNNING → FINISHED_*: проверки остановки в sched/utils.py (check_stop) и update_from_output; прерывание через finish_requests().
  • WAITING → WAITING_FOR_REMOTE_KVS → (WAITING|PREEMPTED): путь async-загрузки через KV-коннектор.

Переходы не охраняются единым объектом конечного автомата — каждый переход — это голый request.status = ..., разбросанный по планировщику (§8, слабое место W2).

3. Планировщик и continuous batching (непрерывное батчирование)

Файлы: vllm/v1/core/sched/{scheduler,async_scheduler,output}.py, vllm/v1/core/{kv_cache_manager,block_pool,kv_cache_coordinator}.py, vllm/v1/kv_cache_interface.py. (Замечание: scheduler.py — ~2370 строк / 109 KB — «большой», но не как runner с 7583 строками.)

3.1 Фазы prefill нет — только цикл догоняющего бюджета токенов

Собственный комментарий планировщика (scheduler.py:~338) формулирует модель: нет фазы decode или prefill; у каждого запроса есть num_computed_tokens и num_tokens_with_spec, и каждый шаг назначает токены так, чтобы num_computed_tokens догонял. schedule() (scheduler.py:336):

  1. token_budget = max_num_scheduled_tokens (ограничение на шаг).
  2. Очередь running — в первую очередь (~372-513): для каждого запроса вычисляется num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens, зажимается до бюджета / порога chunked-prefill, вызывается kv_cache_manager.allocate_slots(...). Если возвращается None — вытесняется запрос с наименьшим приоритетом (или последний) и повторяется попытка.
  3. Очередь waiting — во вторую очередь (~558-851): поиск по prefix-кешу, опциональная удалённая KV-загрузка, расчёт токенов для chunked-prefill, allocate_slots, принятие → RUNNING.
  4. Строится SchedulerOutput; _update_after_schedule() продвигает num_computed_tokens += num_scheduled_tokens и устанавливает is_prefill_chunk.

Continuous batching вытекает из этого: никакого фиксированного батча нет — каждый шаг заново выводит работающее множество, завершённые запросы выпадают, а ожидающие присоединяются.

Chunked prefill — просто зажатие бюджетом: num_new_tokens длинного промпта ограничивается оставшимся token_budget (и long_prefill_token_threshold), поэтому промпт потребляется за несколько шагов по мере продвижения num_computed_tokens.

3.2 Prefix caching (кеширование префиксов)

kv_cache_manager.get_computed_blocks() (kv_cache_manager.py:~196) хеширует последовательность блоков запроса (Request.block_hashes) и вызывает coordinator.find_longest_cache_hit(...), возвращая самый длинный закешированный префикс и количество покрытых им токенов. Хеш-таблица — BlockHashToBlockMap в block_pool.py:~34. Тонкость: поиск обрезает до num_tokens - 1, так что последний токен всегда перевычисляется для получения logit'ов (kv_cache_manager.py:~221).

3.3 KV-cache manager и пул блоков

BlockPool (block_pool.py:~130) владеет всеми num_gpu_blocks объектами KVCacheBlock, FreeKVCacheBlockQueue (порядок вытеснения) и хеш-таблицей prefix-кеша. На запрос: SingleTypeKVCacheManager.req_to_blocks[req_id] — append-only список блоков. allocate_slots() (kv_cache_manager.py:238) — привратник: освобождает блоки вне окна (sliding window), проверяет наличие свободных блоков (возвращает None → инициирует вытеснение), выделяет и кеширует заполненные блоки. Блоки подсчитываются по ссылкам; блок возвращается в очередь свободных только при ref_cnt == 0. Гибридные модели используют несколько kv_cache_groups (см. §7).

3.4 Scheduler vs AsyncScheduler — ключевое различие

AsyncScheduler(Scheduler) (async_scheduler.py:12) переопределяет пост-шаговые bookkeeping-операции (учёт состояния), чтобы движок мог планировать шаг N+1 до того, как вернётся вывод шага N:

  • _update_after_schedule: для каждого не-prefill запроса num_output_placeholders += 1 + cur_num_spec_tokens (async_scheduler.py:31) и request.spec_token_ids = self._spec_token_placeholders (разделяемый список [-1]*num_spec, async_scheduler.py:~16). Это -1 является источником заглушки, которую путь spec-под-PP должен заполнять (см. §8).
  • Под PP также устанавливается next_decode_eligible_step = current_step + pp_size (async_scheduler.py:45) — ограничение следующего шага декодирования запроса в соответствии с ритмом конвейера.
  • _update_request_with_output: num_output_placeholders -= len(new_token_ids); assert num_output_placeholders >= 0 (async_scheduler.py:63-64).
  • prev_step_scheduled_req_ids отслеживает принадлежность к предыдущему батчу — именно тот сигнал, который использует upstream PR #40768 для решения о безопасности вставки заглушки -1.

3.5 Контракт SchedulerOutput (scheduler → executor, на каждый шаг)

SchedulerOutput (sched/output.py:180) содержит: scheduled_new_reqs: list[NewRequestData] (полное состояние, по одному разу на запрос, output.py:31), scheduled_cached_reqs: CachedRequestData (дельты каждый шаг, output.py:111), num_scheduled_tokens: dict[str,int], total_num_scheduled_tokens, scheduled_spec_decode_tokens: dict[str, list[int]] (драфт-токены), num_common_prefix_blocks (cascade-attention),finished_req_ids, preempted_req_ids. Заметим: scheduled_spec_decode_tokens использует неявное «отсутствующий ключ = нет драфтов» (§9, пробел типизации).

4. Цикл движка и режимы батчирования

Файл: vllm/v1/engine/core.py. Здесь фактически происходит конвейеризация PP.

4.1 step_fn выбирается один раз

self.step_fn = self.step if self.batch_queue is None else self.step_with_batch_queue (core.py:217). batch_queue существует тогда и только тогда, когда max_concurrent_batches > 1 (core.py:192-198, это deque(maxlen=...)). max_concurrent_batches (config/vllm.py:497-507) возвращает pp_size в базовом случае, pp_size+1 для async+V2, 2 для async при pp≤1. Таким образом: PP>1 ⇒ batch_queue включён, даже без async. Печально известный комментарий живёт здесь: config/vllm.py:504 — "V1 Model Runner does not fully support async scheduling with PP."

4.2 step() — простой синхронный путь

core.py:443: schedule() → execute_model(non_block=True) → future.result() блокирует (~core.py:461) → update_from_output(). Один батч в полёте; поток движка блокируется на GPU.

4.3 step_with_batch_queue() — конвейерный путь

core.py:484. На каждой итерации:

  1. Если дек не заполнен, планирует новый батч через schedule(), запускает execute_model(non_block=True), выполняет appendleft((future, scheduler_output, exec_future)), и ранний возврат (None, executed) — без ожидания — пока есть работа и в очереди есть место (core.py:~541).
  2. Как только заполнен (или нет новой работы), извлекает самую старую запись через batch_queue.pop() и блокируется на её future.result() (core.py:~555), затем вызывает update_from_output().

Поскольку очередь хранит до pp_size батчей в полёте и применяется только самый старый, update_from_output отстаёт от планирования приблизительно на pp_size − 1 шагов. Эта задержка и есть смысл — она держит все PP-стадии занятыми (заполняет конвейер). SchedulerOutput, захваченный на шаге N, является снимком состояния; spec_token_ids, num_output_placeholders, is_prefill_chunk могут все измениться до того, как соответствующий вывод будет применён через k шагов. Этот window нестабильности — именно то место, где живёт корректность spec-под-PP (кирпич 40).

Есть также ветка deferred_scheduler_output для structured output (откладывает семплинг до применения предыдущего вывода, core.py:~574-596).

4.4 post_step() — SYNC-путь drafte-токенов спекуляции

core.py:474:

def post_step(self, model_executed):
    if not self.async_scheduling and self.use_spec_decode and model_executed:
        draft_token_ids = self.model_executor.take_draft_token_ids()
        if draft_token_ids is not None:
            self.scheduler.update_draft_token_ids(draft_token_ids)

Вызывается на каждой итерации после step_fn (core.py:~1264). Это sync-сантехника спекуляции: извлечь вывод драфтера из исполнителя и передать его планировщику. При async — это no-op: worker напрямую вставляет драфт-токены во входной батч. Два пути не имеют общей абстракции (§8, W4). Кирпич 40 §«Session 5» фиксирует, что sync-путь дедлочит для MTP+PP на текущем main (ранг ждёт вывода спекуляции, который не приходит), тогда как async-путь падает (утечка заглушки -1) — то есть оба режима не завершены для MTP+PP.

4.5 Путь вывода и busy-loop

Выводы попадают в output_queue через put_nowait; демон-поток process_output_sockets сериализует их и отправляет через ZMQ, так что цикл никогда не блокируется на I/O. run_busy_loop (core.py:1216; DP-переопределение core.py:1844) — это синхронный цикл _process_input_queue(); _process_engine_step().

Глубокий разбор: pipeline parallelism

PP разделяет слои модели на смежные стадии по рангам. При L слоях и pp_size стадиях get_pp_indices даёт каждому рангу срез [start, end) — равное разбиение L // pp_size с остатком, переданным средним рангам (последний ранг сохраняет output norm). VLLM_PP_LAYER_PARTITION переопределяет это (рычаг памяти Q13, кирпич 40/70). Что пересекает границу стадии — мало: словарь {hidden_states, residual} на токен, а не тяжёлый per-layer all-reduce как у TP — именно поэтому PP, а не TP выбирается для PCIe-пары без NVLink.

Соглашение о размещении (кирпич 10/20): embed_tokens живёт на первом ранге (или на последнем тоже, если tie_word_embeddings); norm + lm_head — на последнем. Нелокальные слои — это PPMissingLayer (no-op nn.Identity), их веса пропускаются при загрузке. Канонический PP forward (if is_first_rank: embed; else: read intermediate_tensors; ... ; if not is_last_rank: return IntermediateTensors; else norm) — это точный паттерн, который воспроизводит MTP-драфт, и причина, по которой Design C требует флага «standalone draft», чтобы драфт (который работает на последнем ранге, где is_first_rank==False) не попадал в ветку чтения промежуточных тензоров (кирпичи 10/60).

Пузыри. Конвейер имеет пузыри заполнения/слива (первые/последние pp_size−1 шагов, когда не все стадии заняты). vLLM скрывает устойчивые пузыри, держа pp_size батчей в полёте через batch_queue (§4.3). Runner V2 (#42187) дополнительно сокращает пузыри, но недоступен нашей квантованной гибридной Qwen3.5 (кирпич 40: V2 требует not is_moe and not is_quantized и находится в whitelist архитектур).

Композиция. TP×PP образуют сетку (linear.py шардирует внутри стадии, PP — между стадиями). PP×DP реплицируют PP-конвейер на каждый DP-ранг. PP×spec — сложная часть: драфтер работает только на последней стадии, и его сэмплированные токены необходимо широковещательно передать ранним стадиям, чтобы те могли построить следующий вход (§8).

7. KV-кеш и механизм внимания

Файлы: vllm/v1/kv_cache_interface.py, vllm/v1/worker/block_table.py, vllm/v1/core/kv_cache_utils.py, бэкенды внимания.

  • PagedAttention. KV хранится в фиксированных блоках (аналогия с пейджингом ОС). На каждый запрос — таблица блоков (block_table.py:~70, [max_reqs, max_blocks_per_req] int32), отображающая логический индекс блока → физический id блока. На каждый токен — slot mapping (маппинг слотов, block_table.py:~75), задающий физический слот токена block_id * block_size + offset; дополняющие записи используют PAD_SLOT_ID = -1. Бэкенды внимания читают slot mapping для записи/чтения KV без обращения к таблице блоков.
  • Типы KVCacheSpec (kv_cache_interface.py): FullAttentionSpec (~203), SlidingWindowSpec (~459), MLAAttentionSpec (~352, DeepSeek latent), ChunkedLocalAttentionSpec, MambaSpec (~605, SSM/conv-состояние — фиксированная форма, не индексируется по токенам), CrossAttentionSpec, EncoderOnlyAttentionSpec. KVCacheGroupSpec (~837) группирует слои, разделяющие спецификацию; гибридные модели получают несколько групп, дополненных до единого размера страницы.
  • Гибридные модели (mamba/GDN + attention). Qwen3.5 смешивает attention KV с Mamba conv/SSM-состоянием. Слои attention используют paged-блоки; слои Mamba используют фиксированные per-request буферы состояния (без таблицы блоков). _update_states_after_model_execute (gpu_model_runner.py:~1502, только гибридный) вычисляет per-request принятые счётчики (sampled != -1).sum(dim=1) — релевантно для учёта спекуляции (кирпич 80 §3, Q17). GDN-ядра causal_conv1d JIT-компилируются и выполняются (кирпич 70 — не memory wall).
  • KV-профилирование. determine_available_memory запускает фиктивный прямой проход при max_num_batched_tokens, измеряет пиковую память активаций, вычитает её (+ накладные расходы + cudagraph-резервации) из общего VRAM и делит на размер страницы для получения num_gpu_blocks (gpu_model_runner.py путь профилирования + kv_cache_utils.py:~1258). num_gpu_blocks_override обходит это.

Специально для стороны драфта (кирпич 30): MTP-драфт имеет собственные KV-тензоры, но входит в ту же kv_cache_group, что и целевая модель, разделяет таблицы блоков / slot mapping и откатывает отклонения через общий seq_lens (перезапись при повторном использовании, а не явная очистка).

8.2 Rejection sampler (семплер отклонений) = оракул корректности

rejection_sampler.py. Greedy-ядро (rejection_greedy_sample_kernel, :708): target_argmax = target_logits.argmax(-1) (:452); драфт-токен принимается тогда и только тогда, когда совпадает с target argmax, иначе он заменяется на target argmax и всё после него отклоняется. Следовательно, greedy-вывод — это чистая функция от (последовательность target argmax, последовательность драфта) → не зависит от весов: веса влияют только на скорость принятия, но никогда на равенство spec-vs-non-spec. Именно это позволяет dummy/MiMo-весам валидировать каскад (кирпич 70 A3). Не-greedy путь — это истинное вероятностное rejection sampling (проверка отношения к вероятностям драфта).

  • Бонусный токен: если все драфты приняты, целевая модель также выдаёт один дополнительный «бесплатный» токен в конце принятых. Таким образом, ширина выходной сетки — [num_reqs, num_spec + 1].
  • PLACEHOLDER_TOKEN_ID = -1 (rejection_sampler.py:30): валидные токены идут непрерывно начиная со столбца 0; позиции отклонённых/дополнений — -1. parse_output (:247) оставляет != -1 & < vocab (:267).

12. Где наше изменение находится в общей картине

Путь, который мы изменяем, — поток спекулятивных токенов под PP — это тонкий, но несущий шов: последний PP-ранг сэмплирует + запускает rejection oracle, широковещательно передаёт сетку [num_reqs, num_spec+1] ранним рангам, а те реконструируют свой следующий вход из broadcast + снимка планировщика. Это затрагивает §3 (учёт заглушек в планировщике), §4 (k-шаговая задержка batch_queue), §5 (методы runner'а _update_states/_prepare_input_ids/PP transport), §6 (broadcast, написанный вручную) и §8 (rejection oracle как шлюз корректности). Изменение с точки зрения дизайна невелико (Design C: один флаг прямого прохода «standalone draft», кирпич 60); объём и риск — в этой сантехнике корректности (кирпичи 40/80), которая не зависит от дизайна. Наши завершённые автономные результаты — A1c (int4-квантование встраивания драфта при загрузке, memory wall) и B1a (broadcast-транспорт, агностичный по ширине) — и запланированные C0/C1 (исполняемая спецификация + типизированная модель состояний) непосредственно укрепляют W3/W4/W5 и пробелы типизации §9. Дуга вклада C0–C5 и согласование с #40768 — в кирпиче 81.

0. 30-секундная модель шва

При PP>1 + async scheduling (асинхронное планирование) один шаг декодирования спекулятивного запроса разбит по рангам и по времени:

  • Последний ранг запускает sampler (семплер) + rejection oracle (оракул отклонения), производя сетку sampled_token_ids = [num_reqs, num_spec+1] (валидные токены упакованы начиная с колонки 0, -1 — padding после них). Он broadcast-ит эту сетку на остальные ранги и предлагает следующие черновики (drafts).
  • Не-последние ранги никогда не запускают sampler. Они получают сетку и должны восстановить входные данные следующего шага (input_ids) из неё — потому что embedding (таблица вложений) живёт на первом ранге, и следующий токен должен быть заэмбеддирован где-то.
  • Scheduler (планировщик) работает с опережением (async): резервирует spec-слоты с -1 placeholders (заглушками), чтобы можно было запланировать шаг N+1 до того, как вернётся вывод шага N. Движок применяет этот вывод примерно через pp_size−1 шагов (задержка batch_queue).

Всё, что может пойти не так, живёт в разрыве между «последний ранг знает настоящий токен» и «каждый другой ранг, спустя k шагов, нуждается в этом настоящем токене для embedding».

Корневая причина (решающая структурная находка). При async PP ни один путь кода никогда не записывает настоящее значение сэмплированного токена в token_ids_cpu не-последнего ранга. Трейс:

  • _update_states branch-1 (gpu_model_runner.py:1342): для async PP new_token_ids == [] → ничего не дописывает.
  • branch-2 (gpu_model_runner.py:1418): продвигает счётчики и выставляет is_token_ids = True, но запись в token_ids_cpu стоит за if new_token_ids: → False для async PP → значение не записывается.
  • receiver (gpu_model_runner.py:4694): записывает -1 + счётчик, без значения.

5. Почему это не может «просто упроститься»

Очевидное упрощение — «пусть не-последний ранг сам пересчитает токен» — не работает: у не-последнего ранга нет sampler-а и финальных logit-ов (они на последнем ранге, по соглашению PP placement — FOUNDATIONS.md §4/§6). Токен должен передаваться с последнего ранга, а в рамках pipeline — пережить k-шаговую задержку. Второе упрощение — «сделать это синхронным, чтобы не было placeholder-dance» — тоже не работает: sync MTP+PP дедлочится в текущем main (ранг ждёт spec-вывода, который никогда не приходит; PIPELINE-NARRATIVE.md §Move 7). Так что сложность вынужденная: значение должно быть broadcast-ировано (не пересчитано) и сохранено (не транзиентно), при async (не sync). Value-back-write в C4 — минимальное выполнение этого требования. Более глубокая чистка — типизированный SampledTokenGrid, делающий «valid-from-0, никогда не эмбеддировать -1» невыразимо-неверным — это вклад C0/C1, который пенсионирует весь этот класс багов (brick 81).
